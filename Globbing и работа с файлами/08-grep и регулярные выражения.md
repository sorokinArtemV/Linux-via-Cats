# grep и регулярные выражения

> [!abstract] Globbing и работа с файлами · подглава 8 из 9
> Поиск внутри файлов: почему `grep` находит подстроку, а не имя целиком, три несовместимых диалекта регулярок и то, как жадная звёздочка выдирает полстроки вместо одного поля.

`find` ищет файлы по свойствам — имени, размеру, времени. `grep` ищет **внутри** файлов, по содержимому. Это два разных вопроса: «где лежит конфиг nginx» и «в каком из ста конфигов написан этот домен».

Сам по себе `grep` устроен просто: читает строки, печатает те, что подошли под шаблон. Сложность вся в шаблоне — это регулярные выражения, отдельный язык со своей историей, тремя несовместимыми диалектами и репутацией чего-то нечитаемого. Репутация заслужена лишь отчасти: базовых конструкций там десяток, и они закрывают девяносто процентов задач.

Разбирать будем с нуля. Если ты писал регулярки в C# — половину узнаешь, но обрати внимание на раздел про диалекты: то, что работает в .NET, в `grep` без ключа `-E` не заработает.

## Простой случай: поиск без всякого регекса

Начнём с того, что часто регулярка вообще не нужна.

```bash
kot@catbox:~$ grep barsik /var/log/catgallery/access.log
10.0.0.14 - - [03/Sep/2026:11:42:01] "GET /cats/barsik_01.jpg" 200 2413556
10.0.0.14 - - [03/Sep/2026:11:42:09] "GET /cats/barsik_02.jpg" 404 153
```

Шаблон `barsik` — это просто текст. `grep` печатает строки, в которых он встретился. Имя команды, кстати, — это команда из старого редактора `ed`: `g/re/p`, то есть «globally search for regular expression and print».

Первая порция ключей, которые нужны сразу:

| Ключ | Что делает |
| --- | --- |
| `-i` | игнорировать регистр |
| `-n` | показывать номера строк |
| `-c` | вместо строк — их количество |
| `-v` | инвертировать: показать строки **без** совпадения |
| `-w` | совпадение только как отдельное слово |
| `-l` | только имена файлов, где нашлось |
| `-L` | только имена файлов, где **не** нашлось |
| `-o` | печатать не строку, а само совпадение |
| `-q` | ничего не печатать, только код возврата |
| `-F` | шаблон — обычный текст, не регулярка |

Несколько из них используются постоянно и заслуживают комментария.

`-v` — фильтр шума. Смотреть лог, где половина строк от health-check'а мониторинга, невозможно; `grep -v health` убирает их.

`-l` — когда важен не текст, а место. «В каком из конфигов упоминается старый домен» — это `grep -rl old-domain /etc/`.

`-q` — для условий в скриптах. Не печатает ничего, но возвращает 0, если нашлось, и 1, если нет:

```bash
if grep -q 'ssl_certificate' /etc/nginx/nginx.conf; then
    echo "TLS настроен"
fi
```

Кстати, код возврата у `grep` есть всегда: 0 — нашлось, 1 — не нашлось, 2 — ошибка. Это стандартный способ проверять наличие чего-то в скриптах.

`-F` — «искать буквально». Если шаблон содержит точки, скобки или звёздочки, а ты хочешь найти их как есть, `-F` избавляет от экранирования. Заодно он быстрее: без регулярок `grep` использует более прямой алгоритм поиска подстроки.

```bash
kot@catbox:~$ grep -F '192.168.1.1' /var/log/catgallery/access.log
```

## Контекст: `-A`, `-B`, `-C`

При разборе логов совпавшая строка редко бывает самодостаточной. Нужно видеть, что было до и после.

```bash
kot@catbox:~$ grep -B2 -A5 'Traceback' /var/log/catgallery/error.log
```

`-B2` — две строки before, `-A5` — пять after, `-C3` — по три с обеих сторон. Для стектрейсов, где полезное лежит под заголовком, `-A` незаменим.

Между блоками `grep` рисует разделитель `--`, чтобы не сливать несмежные куски.

## Рекурсия: `-r` и что с ней не так

```bash
kot@catbox:~$ grep -rn 'barsik' /srv/cats/
```

`-r` обходит дерево сам, без `find`. Быстро, удобно, и есть пара нюансов.

Первый: `-r` пойдёт **везде**, включая `.git`, `node_modules`, кэши и бинарные файлы. Отсюда ключи фильтрации:

```bash
grep -rn --include='*.conf' 'server_name' /etc/
grep -rn --exclude-dir={.git,node_modules,thumbs} 'TODO' /srv/
```

Второй: бинарные файлы. `grep` их распознаёт и вместо содержимого пишет `Binary file matches`. Ключ `-I` (заглавная i) исключает бинарники из поиска, `-a` наоборот заставляет обрабатывать их как текст — со всеми последствиями для терминала из [[04-Просмотр файлов|четвёртой подглавы]].

Третий, менее известный: `-r` не идёт по символическим ссылкам, а `-R` идёт. Если структура каталогов построена на симлинках — нужна заглавная.

> [!tip] `grep -r` или `find | xargs grep`
> Оба работают. `grep -r` короче и обычно быстрее — один процесс вместо конвейера. Но когда нужен отбор по свойствам файла, а не по имени, обход отдаёт `find`:
>
> ```bash
> find /srv -type f -newermt '1 hour ago' -print0 | xargs -0 -r grep -l 'ERROR'
> ```
>
> «Файлы, изменённые за последний час, где есть ERROR» — через `--include` такое не выразить.
>
> И если на машине есть `ripgrep` (`rg`), для поиска по кодовой базе он в разы быстрее и по умолчанию уважает `.gitignore`. Но `grep` есть везде, а `rg` — нет.

## Регулярные выражения с нуля

Теперь про сам язык шаблонов.

Регулярное выражение описывает **множество строк**. Движок берёт строку и проверяет, есть ли в ней кусок, подходящий под описание. Ключевое слово — «кусок»: в отличие от глоббинга, где шаблон сопоставляется с именем целиком, регулярка ищет **подстроку** в любом месте.

Это первое, обо что спотыкаются:

![[glob-12-glob-vs-regex.png]]
*Рис. 8.1. Glob сопоставляется с именем целиком, regex — с любым куском строки. И точка в regex значит «любой символ», поэтому `.jpg` ловит и `_jpg`.*

Обе особенности работают вместе и дают самую частую ошибку новичка. Шаблон `barsik.jpg` совпадёт с `barsikXjpg`, `barsik_jpg` и с любой строкой, где эти буквы идут подряд с одним произвольным символом посередине.

Теперь по кирпичикам.

**Обычные символы** совпадают сами с собой. `barsik` — это шесть символов подряд.

**Точка `.`** — любой один символ, кроме перевода строки. Чтобы найти настоящую точку, её экранируют: `\.`.

```bash
kot@catbox:~$ grep 'barsik\.jpg' access.log      # именно точка
kot@catbox:~$ grep -F 'barsik.jpg' access.log    # то же самое, проще
```

**Якоря `^` и `$`** привязывают шаблон к началу и концу строки:

```bash
grep '^10\.0\.0\.' access.log        # запросы из подсети 10.0.0.x
grep ' 500$' access.log              # строки, кончающиеся кодом 500
grep '^$' config.conf                # пустые строки
grep -vE '^\s*#|^$' /etc/nginx/nginx.conf   # конфиг без комментариев и пустот
```

Последняя строка — приём, которым пользуются постоянно: убрать из конфига весь шум и посмотреть, что там реально настроено.

**Наборы `[…]`** — один символ из перечисленных. Синтаксис почти как в глоббинге, с одним отличием: отрицание пишется через `^`, а не через `!`.

```bash
grep '[0-9][0-9][0-9]' access.log       # три цифры подряд
grep '[^0-9]' data.txt                  # строки, где есть не-цифра
```

POSIX-классы работают и здесь: `[[:digit:]]`, `[[:alpha:]]`, `[[:space:]]`. Те же самые, что во [[02-Продвинутые шаблоны|второй подглаве]].

**Квантификаторы** — сколько раз повторяется предыдущий элемент:

| Запись | Значение |
| --- | --- |
| `*` | ноль или больше раз |
| `+` | один или больше раз |
| `?` | ноль или один раз |
| `{3}` | ровно три раза |
| `{2,5}` | от двух до пяти |
| `{2,}` | два и больше |

Вот здесь и живёт главное расхождение с глоббингом. В шаблоне оболочки `*` означал «любая последовательность символов» сам по себе. В регулярке `*` — это модификатор для того, что стоит слева. Аналог глобовой звёздочки — `.*`: «любой символ, сколько угодно раз».

**Группировка `( )` и альтернатива `|`**:

```bash
grep -E 'barsik|murka|ryzhik' access.log        # любой из трёх
grep -E '(GET|POST) /cats/' access.log          # два метода
grep -E '^(10|192)\.' access.log                # адреса из двух подсетей
```

Ключ `-E` здесь не случаен, и вот почему.

## Три диалекта, или почему `-E` нужен всегда

Регулярные выражения существуют с шестидесятых, и стандартизировали их поздно и дважды. В результате в системе живут три несовместимых диалекта.

**BRE** (Basic Regular Expressions) — то, что `grep` понимает по умолчанию. Древний вариант, где `+`, `?`, `{}`, `()` и `|` **не являются** специальными символами и требуют экранирования обратным слэшем, чтобы получить своё специальное значение.

**ERE** (Extended) — включается ключом `-E` (или командой `egrep`, которая объявлена устаревшей). Здесь всё наоборот: специальные символы пишутся как есть, а для буквального значения экранируются.

**PCRE** (Perl-Compatible) — включается ключом `-P`, если `grep` собран с поддержкой. Самый богатый: тут есть `\d`, `\b`, ленивые квантификаторы, lookahead — всё, к чему привык человек из .NET или JavaScript.

Одно и то же выражение в трёх видах:

| Задача | BRE (по умолчанию) | ERE (`-E`) | PCRE (`-P`) |
| --- | --- | --- | --- |
| Один или больше | `a\+` | `a+` | `a+` |
| Ноль или один | `a\?` | `a?` | `a?` |
| Группа | `\(ab\)` | `(ab)` | `(ab)` |
| Альтернатива | `a\|b` со слэшем | `a\|b` | `a\|b` |
| Ровно три раза | `a\{3\}` | `a{3}` | `a{3}` |
| Цифра | `[0-9]` | `[0-9]` | `\d` |
| Граница слова | `\b` | `\b` | `\b` |

Логика BRE выглядит вывернутой наизнанку, и она такая и есть: в семидесятых `+` и `?` в шаблонах не существовали вовсе, а когда их добавили — уже нельзя было ломать совместимость с миллионом строк, где эти символы означали сами себя.

> [!tip] Пиши `grep -E` по умолчанию
> Привыкни всегда добавлять `-E`. Тогда синтаксис совпадает с тем, что ты видел в других языках, и не нужно помнить, где ставить слэши. Разница в производительности между BRE и ERE отсутствует.
>
> `-P` бери, когда нужны `\d`, `\b`, `\s` или lookahead. Но помни, что `-P` есть не везде: в busybox (то есть в Alpine-контейнерах) и на macOS его нет. Скрипт с `grep -P` может не завестись там, где ты не ожидаешь.

Отдельно про `sed` и `awk`: `sed` по умолчанию тоже BRE, `sed -E` даёт ERE, а `awk` всегда ERE. То есть шаблон, работающий в `grep -E`, скорее всего заработает и в `awk`, но не в `sed` без ключа.

## Жадность

Квантификаторы `*` и `+` **жадные**: они захватывают максимально длинный кусок, какой позволяет остальная часть шаблона.

Классический пример — выдрать первое поле в кавычках из строки лога:

```bash
kot@catbox:~$ grep -oE '".*"' access.log | head -1
"GET /cats/barsik_01.jpg" 200 2413556 "Mozilla/5.0 (X11; Linux)"
```

Ожидался запрос, а пришла почти вся строка. Шаблон `".*"` прочитан как «кавычка, потом что угодно, потом кавычка» — и «что угодно» растянулось до **последней** кавычки в строке, а не до первой.

![[glob-13-zhadnost.png]]
*Рис. 8.2. `".*"` доходит до последней кавычки в строке. `"[^"]*"` физически не может перескочить через кавычку и останавливается на первой.*

Способа два. В PCRE есть ленивый квантификатор `*?`, который берёт минимально возможное:

```bash
kot@catbox:~$ grep -oP '".*?"' access.log | head -1
"GET /cats/barsik_01.jpg"
```

Способ, работающий везде, включая ERE, — вместо «что угодно» написать «что угодно, кроме закрывающего символа»:

```bash
kot@catbox:~$ grep -oE '"[^"]*"' access.log | head -1
"GET /cats/barsik_01.jpg"
```

`[^"]*` физически не может перескочить через кавычку, поэтому и жадничать некуда. Эта конструкция — `[^X]*X` — универсальная идиома для «до ближайшего X», и она обычно ещё и быстрее ленивого квантификатора.

## Полезные конвейеры

Несколько связок, которые окупаются на любом разборе:

```bash
# топ IP-адресов по числу запросов
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# все уникальные коды ответов
grep -oE '" [0-9]{3} ' access.log | sort -u

# ошибки за последний час (лог с ISO-датами)
grep "$(date -d '1 hour ago' '+%Y-%m-%dT%H')" error.log

# найти, где определена директива, во всём дереве конфигов
grep -rn --include='*.conf' -E '^\s*server_name' /etc/nginx/

# файлы, где НЕТ нужной строки — частая задача при аудите
grep -rL 'ssl_protocols' /etc/nginx/sites-enabled/
```

Связка `sort | uniq -c | sort -rn` — это «топ по частоте», и она встречается в разборе логов постоянно. Запомни её целиком: `uniq` без предварительного `sort` не работает, потому что схлопывает только соседние одинаковые строки.

Про `awk` в первой строке: он умеет разбирать строку на поля по пробелам, и `$1` — первое поле. Полноценно `awk` и `sed` — тема отдельной главы, [[Потоковая обработка текста]], но эта одна конструкция окупается сразу.

## Что нужно унести из этой подглавы

Прежде чем пойдём ломать, проверь себя:

> [!summary] Семь утверждений
> 1. `grep` ищет **подстроку** в любом месте строки, а не совпадение целиком. Это главное отличие от глоббинга, и оно порождает большинство ложных срабатываний.
> 2. В регулярке `.` — любой символ, а `*` — модификатор для предыдущего элемента. Аналог глобовой звёздочки — `.*`.
> 3. Диалектов три. `grep` по умолчанию — архаичный BRE, где `+`, `?`, `()`, `{}` требуют слэша. Привыкай писать `-E`.
> 4. `-P` даёт `\d`, `\b` и ленивые квантификаторы, но есть не везде: в Alpine и на macOS его нет.
> 5. Квантификаторы жадные. Универсальный приём против этого — `[^X]*X` вместо `.*X`, он работает в любом диалекте.
> 6. Ключи, которые окупаются каждый день: `-i`, `-n`, `-v`, `-w`, `-l`, `-c`, `-o`, `-q`, `-F`, `-A`/`-B`/`-C`.
> 7. Связка `sort | uniq -c | sort -rn | head` даёт топ по частоте. `uniq` без предварительного `sort` не работает.

## Как это ломается

### «В логе восемнадцать тысяч пятисоток»

Галерея на `catbox` отдаёт ошибки. Задача — понять, на каких запросах.

Первая попытка:

```bash
kot@catbox:~$ grep 500 /var/log/catgallery/access.log | wc -l
18432
```

Восемнадцать тысяч при шестистах тысячах запросов за сутки — это три процента ошибок, и такое давно заметил бы мониторинг. Смотрим, что нашлось:

```bash
kot@catbox:~$ grep 500 access.log | head -2
10.0.0.14 - - [03/Sep/2026:11:42:01] "GET /cats/barsik_01.jpg" 200 2413500
10.0.0.14 - - [03/Sep/2026:11:42:03] "GET /cats/murka.jpg" 200 1500302
```

Обе строки с кодом 200. Число `500` нашлось внутри размера ответа — `grep` ищет подстроку где угодно, и никакой семантики «это поле статуса» у него нет.

Уточняем через позицию. Код ответа в этом формате стоит сразу после кавычки запроса, отделённый пробелами:

```bash
kot@catbox:~$ grep -E '" 500 ' access.log | wc -l
47
```

Сорок семь — правдоподобно. Смотрим, что за URL:

```bash
kot@catbox:~$ grep -E '" 500 ' access.log | grep -oE '"[A-Z]+ [^"]*"' | sort | uniq -c | sort -rn | head
     41 "GET /cats/2019/summer/pushok_raw.tiff"
      4 "GET /cats/2020/full_backup.tar"
      2 "GET /cats/thumbs/"
```

Виноваты гигантские файлы — те самые, что нашлись в [[05-Счёт|пятой подглаве]] при разборе диска. Сервис пытается отдать полуторагигабайтный TIFF и падает по таймауту или памяти.

> [!warning] Подстрока без якорей находит лишнее
> Это та же ошибка, что искать пользователя `grep root /etc/passwd` и получить `nonroot`, `rootless`, `chroot-user`. Три способа сузить:
>
> - `-w` — совпадение как отдельное слово: `grep -w root`;
> - `-x` — совпадение со всей строкой целиком;
> - якоря и контекст: `grep '^root:'`.
>
> Каждый раз, когда `grep` находит подозрительно много, первая мысль должна быть «шаблон недостаточно привязан к позиции».

### «Мониторинг перестал видеть ошибки»

В скрипте проверки здоровья галереи стоит счётчик пятисоток за последний час:

```bash
errors=$(grep -c '" (500|502|504) ' /var/log/catgallery/access.log)
if [ "$errors" -gt 10 ]; then
    echo "ALERT: $errors ошибок"
fi
```

Скрипт никогда не срабатывает, хотя сервис регулярно падает. Проверяем руками:

```bash
kot@catbox:~$ grep -c '" (500|502|504) ' access.log
0
kot@catbox:~$ grep -cE '" (500|502|504) ' access.log
47
```

Одна буква разницы. Без `-E` `grep` работает в диалекте BRE, где скобки и вертикальная черта — **обычные символы**. То есть первая команда честно искала строку, в которой буквально написано `" (500|502|504) ` со скобками и палками. Такой строки в логе нет, поэтому ноль — и ни одной ошибки, ни одного предупреждения: с точки зрения `grep` шаблон корректен, просто ничего не нашлось.

Это самый коварный вид ошибки во всей подглаве: результат правдоподобен. Ноль совпадений выглядит как «ошибок нет», а не как «шаблон не работает».

Проверять такое надо на заведомо совпадающей строке, а не на большом логе:

```bash
kot@catbox:~$ echo '... "GET /x" 500 123' | grep '" (500|502|504) '
kot@catbox:~$ echo '... "GET /x" 500 123' | grep -E '" (500|502|504) '
... "GET /x" 500 123
```

Две секунды, и диагноз готов. Починка — добавить `-E`; заодно стоит пройтись по всем шаблонам в скриптах и проверить, нет ли там `+`, `?`, `{}` или `|` без него.

### «Отчёт по частоте URL показывает мусор»

Ночной отчёт строит топ запросов, на которых сервис падает:

```bash
grep -E '" 500 ' access.log | grep -oE '".*"' | sort | uniq -c | sort -rn | head
```

В отчёте вместо десятка URL — сотни строк, каждая встретилась один раз, и все они разной длины:

```bash
      1 "GET /cats/barsik_01.jpg" 200 2413556 "Mozilla/5.0 (X11; Linux x86_64)"
      1 "GET /cats/barsik_02.jpg" 200 1882301 "Mozilla/5.0 (Macintosh; Intel)"
```

Причина — жадность. Шаблон `".*"` захватил от первой кавычки до последней, то есть запрос вместе с кодом, размером и user-agent'ом. А раз в каждой строке свой user-agent и свой размер, одинаковых значений почти нет — и `uniq -c` схлопывать нечего.

Смотрим, что именно выдирается, ключом `-o` на одной строке:

```bash
kot@catbox:~$ head -1 access.log | grep -oE '".*"'
"GET /cats/barsik_01.jpg" 200 2413556 "Mozilla/5.0 (X11; Linux x86_64)"
kot@catbox:~$ head -1 access.log | grep -oE '"[^"]*"'
"GET /cats/barsik_01.jpg"
"Mozilla/5.0 (X11; Linux x86_64)"
```

Второй вариант вернул два отдельных поля вместо одного склеенного. Теперь отчёт собирается правильно — берём только то поле, где есть метод:

```bash
grep -E '" 500 ' access.log | grep -oE '"[A-Z]+ [^"]*"' | sort | uniq -c | sort -rn | head
```

Общее правило: **если совпадение оказалось длиннее ожидаемого — виновата жадность**, и лечится она заменой `.*` на `[^X]*`, где `X` — тот символ, до которого нужно дойти.

### «Якорь `$` не срабатывает»

Ищем в конфиге строки, заканчивающиеся точкой с запятой, — простая проверка, что директивы дописаны:

```bash
kot@catbox:~$ grep -c ';$' /etc/nginx/sites-enabled/catgallery
0
kot@catbox:~$ grep -c ';' /etc/nginx/sites-enabled/catgallery
23
```

Двадцать три строки с точкой с запятой, и ни одна не заканчивается на неё. Так не бывает — значит, после `;` в каждой строке есть что-то ещё, невидимое.

Инструмент известен из [[04-Просмотр файлов|четвёртой подглавы]]:

```bash
kot@catbox:~$ head -3 /etc/nginx/sites-enabled/catgallery | cat -A
server {^M$
    listen 80;^M$
    server_name cats.local;^M$
```

Конфиг залили из Windows. Перед каждым `\n` стоит `\r`, и с точки зрения `grep` строка заканчивается именно на него — `;` оказывается предпоследним символом. Якорь `$` привязывается к концу строки, а там возврат каретки.

Два выхода. Правильный — починить файл:

```bash
kot@catbox:~$ sudo sed -i 's/\r$//' /etc/nginx/sites-enabled/catgallery
kot@catbox:~$ grep -c ';$' /etc/nginx/sites-enabled/catgallery
23
```

Временный, когда файл править нельзя, — учесть `\r` в самом шаблоне:

```bash
kot@catbox:~$ grep -cE ';\r?$' /etc/nginx/sites-enabled/catgallery
23
```

Та же болезнь ломает не только `$`. Сравнение `[ "$mode" = "fast" ]` в скрипте не сработает, потому что справа на самом деле `fast\r`; шебанг `#!/bin/bash\r` даст `bad interpreter`. Когда что-то не совпадает вопреки очевидности — первым делом `cat -A`.

## Диагностика

Когда `grep` находит не то:

1. **Слишком много совпадений** — шаблон не привязан к позиции. Добавь `-w`, `^`, `$` или контекст вроде `" 500 `.
2. **Ноль совпадений там, где точно есть** — проверь регистр (`-i`) и диалект. Шаблон с `+`, `?`, `(` или `|` без ключа `-E` работает не так, как ты думаешь: `grep 'a+'` ищет буквально «a плюс».
3. **Проверь шаблон на одной строке**, а не на целом логе: `echo 'тестовая строка' | grep -E 'шаблон'`. Быстрее, чем гадать по большому файлу.
4. **Посмотри, что именно совпало**, ключом `-o`. Если совпадение оказалось длиннее ожидаемого — это жадность, замени `.*` на `[^X]*`.
5. **Не срабатывает якорь `$`** — вероятно, в файле виндовые переводы строк. Проверь через `cat -A`.
6. **`Binary file matches` вместо строк** — добавь `-a`, чтобы обработать как текст, или `-I`, чтобы исключить бинарники из рекурсивного поиска.
7. **Рекурсия идёт вечно** — ограничь через `--include` и `--exclude-dir` или отдай обход `find` с нужными предикатами.
8. **Ищешь спецсимволы** — не воюй с экранированием, возьми `-F`.

## Задачи для самопроверки

Всё делается на своей VM с Ubuntu 24.04 или RHEL 9.

> [!question] Задача 1 · Подстрока против целого
> Создай файл со строками `root`, `nonroot`, `chroot-user`, `root:x:0:0`. Сравни, что находят `grep root`, `grep -w root`, `grep '^root'` и `grep -x root`.
>
> **Как понять, что получилось:** четыре разных набора строк, и ты можешь предсказать каждый до запуска.

> [!question] Задача 2 · Диалекты
> На строке `aaa+bbb` проверь `grep 'a+'`, `grep -E 'a+'`, `grep 'a\+'` и `grep -F 'a+'`.
>
> **Как понять, что получилось:** ты можешь сказать, какие из четырёх нашли буквальный плюс, какие — повтор буквы, и почему в BRE смысл слэша обратный привычному.

> [!question] Задача 3 · Жадность
> Возьми строку `"first" middle "second"` и прогони по ней `grep -oE '".*"'`, `grep -oE '"[^"]*"'` и, если есть `-P`, `grep -oP '".*?"'`.
>
> **Как понять, что получилось:** первый вариант даёт одно длинное совпадение, два других — два коротких, и ты можешь объяснить, почему `[^"]*` не может перескочить кавычку.

> [!question] Задача 4 · Топ по частоте
> Возьми любой лог (`/var/log/syslog` подойдёт) и собери топ-5 программ, которые в него пишут: вырежи нужное поле через `grep -oE` или `awk`, дальше `sort | uniq -c | sort -rn | head -5`.
>
> **Как понять, что получилось:** числа в первой колонке убывают, а если убрать первый `sort` — результат рассыпается, и ты можешь объяснить почему.

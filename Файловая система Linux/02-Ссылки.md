# Ссылки

> [!abstract] Файловая система Linux · подглава 2 из 6
> Два способа сослаться на файл, два счётчика, которые держат его живым, и почему удалённый лог продолжает занимать двадцать гигабайт.

[[01-Что такое файл|В прошлой подглаве]] мы выяснили странную вещь: имя файла и сам файл — разные объекты. Файл — это карточка, inode. Имя — строка в таблице каталога. Между ними только номер.

Тогда это выглядело как любопытная деталь устройства. Сейчас окажется, что на этой детали держится половина того, что администратор делает руками каждый день — и половина того, что у него ломается.

Логика простая. Если имя — всего лишь строка с номером, то:

- ничто не мешает завести **две строки с одним номером**;
- ничто не мешает завести строку, которая вместо номера хранит **другое имя**;
- и стоит понять, что будет, если **убрать строку** — что тогда станет с карточкой.

Три вопроса — три раздела этой подглавы. Начнём с модели, чтобы потом не путаться в командах.

## Два способа сослаться на файл

> [!tip] Если совсем на пальцах
> Ключ ко всему: **имя файла — это не файл**. Файл — это inode: номер, метаданные и указатели на блоки с данными. А имя в каталоге — просто запись «строка → номер inode».
>
> Дальше всё выводится из одной этой мысли:
>
> - **Хардлинк** — ещё одна такая запись на _тот же самый_ inode. Не копия и не ссылка на файл, а второе полноправное имя. «Оригинала» и «ссылки» здесь нет, имена равны.
> - **Симлинк** — отдельный маленький файл со своим inode, внутри которого лежит просто **строка с путём**. Ядро при обращении читает эту строку и идёт по ней заново.

![[link-basics.png]]
*Рис. 2.1. `file.txt` и `backup.txt` — два имени одного inode, счётчик ссылок 2. `link.txt` — отдельный файл, внутри которого написано «file.txt».*

Теперь то же самое, но строже — дальше нам понадобится точность. Способов ровно два, и главное различие между ними такое:

> [!important] Главное
> **Жёсткая ссылка указывает на карточку. Символическая — на строку пути.**

То есть они цепляются за разные звенья цепочки `имя → карточка → данные`, которую мы построили [[01-Что такое файл|в прошлой подглаве]].

Жёсткая ссылка — это просто **ещё одно имя** для той же карточки. Никакого нового файла не появляется; появляется вторая строчка в таблице какого-то каталога, и в ней стоит тот же самый номер. Отличить «настоящее» имя от «ссылки» невозможно, потому что различия нет.

Символическая ссылка — это **отдельный, самостоятельный файл**, у которого своя карточка, свой номер и своё содержимое. И содержимое это — текстовая строка с путём. Всё. Симлинк не знает ни про какой inode, он знает буквы.

Отсюда вытекает почти всё остальное, и удобнее увидеть это сразу таблицей:

| Свойство                          | Жёсткая ссылка                            | Символическая ссылка          |
| --------------------------------- | ----------------------------------------- | ----------------------------- |
| Указывает на                      | номер карточки                            | строку пути                   |
| Свой inode                        | нет, это второе имя                       | да, отдельный файл типа `l`   |
| Через границу файловой системы    | нельзя                                    | можно                         |
| На каталог                        | нельзя                                    | можно                         |
| Может «повиснуть в пустоте»       | нет, никогда                              | да, легко                     |
| Есть ли «оригинал»                | нет, имена равноправны                    | да, у ссылки есть цель        |
| Переживёт переименование цели     | да                                        | нет                           |
| Видна ли в `ls -l`                | никак не отличается от обычного файла     | видна: тип `l` и стрелка      |
| Сколько занимает места            | ~0, только строка в каталоге              | ~0, но со своим inode         |

Если из этой подглавы запомнить одну строку — пусть это будет первая. Остальные из неё выводятся, и дальше мы каждую проверим руками.

## Жёсткая ссылка: одно и то же под другим именем

На `catbox` я хочу собрать папку `/srv/cats/best/` с лучшими фотографиями — не копируя трёхмегабайтные JPEG'и и не тратя место дважды. Для этого есть `ln`:

```bash
kot@catbox:/srv/cats$ ln 2024/murzik.jpg best/murzik.jpg
kot@catbox:/srv/cats$ ls -li 2024/murzik.jpg best/murzik.jpg
1310726 -rw-r--r-- 2 kot kot 3145728 Aug 30 21:14 2024/murzik.jpg
1310726 -rw-r--r-- 2 kot kot 3145728 Aug 30 21:14 best/murzik.jpg
```

Один и тот же номер карточки. Один и тот же размер, права, время — и не потому, что `ln` их аккуратно скопировал, а потому что **это один объект, показанный дважды**.

`ln` не создал вообще ничего, кроме строки в таблице каталога `best`. Изменилась одна цифра — вторая колонка, было `1`, стало `2`. Это тот самый `Links` из `stat`: счётчик имён, указывающих на эту карточку.

![[hardlink-vs-symlink.svg]]
*Рис. 2.2. Слева — два имени на одну карточку. Справа — отдельный файл, внутри которого лежит строка пути.*

Одну мысль здесь надо поймать отдельно: **у жёсткой ссылки нет «оригинала»**. Имя `2024/murzik.jpg` ничем не главнее, чем `best/murzik.jpg`, — просто оно появилось раньше, и файловая система об этом даже не помнит. Отредактируй файл через любое из имён, и изменения видны через другое: редактировать-то нечего, кроме одной карточки и её блоков. Удали любое из имён — второе продолжит работать, как ни в чём не бывало.

### Два ограничения, и оба неслучайны

**Первое: оба имени должны лежать на одной файловой системе.** Номер карточки имеет смысл только внутри своей ФС — мы это видели [[01-Что такое файл|в прошлой подглаве]]. Строка в каталоге хранит только номер, без указания устройства, так что указать «наружу» она физически не может:

```bash
kot@catbox:~$ ln /srv/cats/2024/murzik.jpg /mnt/nas/murzik.jpg
ln: failed to create hard link '/mnt/nas/murzik.jpg': Invalid cross-device link
```

**Второе: нельзя делать жёсткую ссылку на каталог.** Даже под root. Причина не в правах, а в геометрии.

Дерево каталогов — это дерево, потому что у каждого каталога один родитель. Если разрешить каталогу `a` содержать ссылку на каталог `b`, а `b` — на `a`, дерево превращается в граф с циклом, и `find`, `du`, `rm -r` и `fsck` уходят по нему в бесконечность. Вдобавок у каждого каталога есть запись `..`, а она одна — при двух родителях просто непонятно, куда ей указывать.

Поэтому единственные жёсткие ссылки на каталоги создаёт само ядро, и мы их уже видели: это `.` и `..`.

### Фокус со счётчиком у каталогов

Отсюда — маленький практический трюк. Посмотри на счётчик имён у каталога:

```bash
kot@catbox:/srv$ ls -ld cats
drwxr-xr-x 4 kot kot 4096 Aug 30 21:14 cats
```

Четвёрка. Откуда, если каталог `cats` в системе один?

1. Имя `cats` в таблице `/srv`.
2. Запись `.` внутри самого `cats` — она указывает на него же.
3. Запись `..` внутри `2023`.
4. Запись `..` внутри `2024`.

Каждый подкаталог добавляет родителю единицу — своим `..`. Значит, **число подкаталогов всегда равно `Links − 2`**, и узнать его можно одним `ls -ld`, без обхода каталога. На больших деревьях это заметно быстрее, чем `find -maxdepth 1 -type d | wc -l`.

Оговорка: правило верно для ext4 и XFS, но не универсально. На btrfs у каталога всегда стоит `1`, сколько бы подкаталогов в нём ни было, а на ext4 счётчик фиксируется на единице, если подкаталогов больше 65 000. Увидев `1`, не делай вывод, что подкаталогов нет, — просто посчитай их обычным способом.

![[dir-link-count.svg]]
*Рис. 2.3. Откуда у каталога берётся четвёрка: имя в родителе, собственная `.` и по одной `..` из каждого подкаталога.*

> [!tip] Кто рвёт жёсткие ссылки
> `sed -i` и многие другие «редактирующие на месте» инструменты на самом деле пишут новый файл рядом и переименовывают его поверх старого. Получается **новая карточка**. Если у файла было два имени, второе останется указывать на старую карточку со старым содержимым, а `Links` у неё станет 1 — связь порвана, и молча.
>
> Vim это умеет замечать и в таком случае пишет в файл напрямую, но полагаться на такое поведение не стоит. Если ты держишь конфиги на жёстких ссылках — правь их через `>` (перезапись существующей карточки) и проверяй `ls -li` после.

## Символическая ссылка: файл, внутри которого путь

Теперь второй способ.

```bash
kot@catbox:/srv/cats$ ln -s 2024/murzik.jpg latest.jpg
kot@catbox:/srv/cats$ ls -li latest.jpg 2024/murzik.jpg
1310740 lrwxrwxrwx 1 kot kot      15 Sep  1 10:02 latest.jpg -> 2024/murzik.jpg
1310726 -rw-r--r-- 2 kot kot 3145728 Aug 30 21:14 2024/murzik.jpg
```

Здесь всё иначе, и это видно по каждой колонке:

- **Номер другой.** 1310740 — у `latest.jpg` своя собственная карточка. Это отдельный файл.
- **Тип `l`.** Один из тех семи типов, что мы разбирали.
- **Размер 15 байт.** Это ровно длина строки `2024/murzik.jpg` — пятнадцать символов. Содержимое симлинка **и есть** эта строка, ничего больше в нём нет.
- **`Links` у Мурзика не изменился**, остался 2 от прошлого раздела. Симлинк не знает ни о какой карточке 1310726 и никак на неё не влияет — он знает только текст.
- **Права `rwxrwxrwx`.** У симлинка они всегда такие, и ядро их полностью игнорирует. Значение имеют права того, куда ссылка ведёт.

Когда программа открывает `latest.jpg`, ядро читает строку из симлинка и **начинает разрешать путь заново** — тем самым пошаговым обходом [[01-Что такое файл|из прошлой подглавы]]. Если путь внутри относительный, отсчёт идёт от того каталога, где лежит сам симлинк.

Из этого — два свойства, которых у жёстких ссылок нет и быть не может:

- Симлинк может вести **куда угодно**: на другую файловую систему, на каталог, на файл, которого ещё не существует. Строку можно написать любую.
- Симлинк может **сломаться**. Если то, куда он ведёт, переименовали или удалили, ссылка остаётся на месте — а за ней пустота.

### Относительный или абсолютный — это решение, а не мелочь

Внутрь симлинка можно записать как относительный путь, так и абсолютный, и последствия у них разные:

- `ln -s 2024/murzik.jpg latest.jpg` — переживёт перенос всего `/srv/cats` на другой диск: и ссылка, и цель уедут вместе, а взаимное расположение не изменится.
- `ln -s /srv/cats/2024/murzik.jpg latest.jpg` — не переживёт.
- Зато относительная ссылка сломается, если переместить **только её саму** в другой каталог.

Правило, которое покрывает почти все случаи: ссылка внутри одного дерева — относительная; ссылка «наружу», в другую часть системы, — абсолютная.

### Как смотреть сквозь ссылку

```bash
kot@catbox:/srv/cats$ readlink latest.jpg              # что записано внутри
2024/murzik.jpg

kot@catbox:/srv/cats$ readlink -f latest.jpg           # куда это ведёт на самом деле
/srv/cats/2024/murzik.jpg

kot@catbox:/srv/cats$ stat -c '%N  %s' latest.jpg      # сам симлинк
'latest.jpg' -> '2024/murzik.jpg'  15

kot@catbox:/srv/cats$ stat -L -c '%N  %s' latest.jpg   # то, куда он ведёт
'latest.jpg'  3145728
```

Ключ `-L` есть у `stat`, у `ls`, у `cp` и у `rsync`, и везде значит одно и то же: **идти по ссылке, а не смотреть на неё**. Это особенно важно при копировании: `cp -r` по умолчанию копирует симлинки как симлинки, строкой. Если внутри был абсолютный путь в старое место — в копии он будет вести туда же.

### Когда что использовать

Практический ориентир, чтобы не выбирать каждый раз заново.

**Символическая — почти всегда.** Она понятна человеку, видна в `ls -l`, работает между разделами и переключается одной командой. На ней стоит половина того, что ты каждый день видишь в системе:

- `/etc/nginx/sites-enabled/site` → `../sites-available/site`: включить и выключить конфиг — это переставить ссылку;
- атомарный деплой: каталоги `releases/2026-09-02/` и ссылка `current` на нужный из них. Выкатка — переставить ссылку, откат — переставить обратно, и то и другое мгновенно;
- `/usr/bin/python3` → `python3.12` и весь механизм `update-alternatives`;
- dotfiles: репозиторий с конфигами плюс симлинки в `~`.

**Жёсткая — узкие специальные случаи**, где данные не должны дублироваться физически, но каждое имя обязано жить самостоятельно:

- инкрементальные бэкапы через `rsync --link-dest`: неизменившиеся файлы не копируются, а хардлинкаются на предыдущий снапшот. Каждый снапшот выглядит полным, а места занимает как разница;
- дедупликация в пакетных менеджерах: pnpm держит один общий store и хардлинкает файлы в `node_modules`;
- ротация логов старой школы: сделать `app.log.1` вторым именем, а оригинал обрезать — процесс с открытым дескриптором ничего не заметит.

Правило, которое покрывает почти всё: **нужна ссылка «на смысл» — на актуальную версию, на выбранный вариант — символическая. Нужна экономия места при физически одинаковых данных — жёсткая.**

И ещё одно соображение, про которое легко забыть: жёсткая ссылка невидима. Посмотрев на файл, ты не узнаешь, есть ли у него второе имя и где оно. Если связь должна быть очевидна человеку — только символическая.

## Что держит файл живым: два счётчика

Теперь третий вопрос — что происходит, когда имя убирают. Здесь понадобится ещё одна модель, зато последняя, и она объясняет сразу все инциденты из этой подглавы.

> [!important] Два счётчика
> **У файла два счётчика.** Первый — сколько **имён** на него указывает. Второй — сколько процессов держат его **открытым**. Файл жив, пока хотя бы один из них больше нуля.

Первый счётчик видно в `stat`, это `Links`. Второго не видно нигде в файловой системе — он живёт только в памяти ядра, потому что описывает не диск, а текущую жизнь системы.

`rm` уменьшает первый. Закрытие файла или смерть процесса уменьшает второй. Когда оба обнулились, ядро освобождает карточку и блоки.

### Поэтому команда называется unlink

Посмотрим, что на самом деле делает `rm`:

```bash
kot@catbox:/srv/cats$ strace -e trace=unlink,unlinkat rm best/murzik.jpg
unlinkat(AT_FDCWD, "best/murzik.jpg", 0) = 0
+++ exited with 0 +++
```

Системного вызова «удалить файл» в Linux **нет**. Есть `unlink` — «отцепить имя». Ядро находит строку в таблице каталога, удаляет её и уменьшает первый счётчик на единицу.

Стал нулём — карточка и блоки помечаются свободными (если второй счётчик тоже нулевой). Не стал нулём — как у Мурзика, у которого осталось имя `2024/murzik.jpg`, — не происходит вообще ничего больше.

Вот почему `rm` жёсткой ссылки безопасен: он убирает имя, а не данные.

### Файл без единого имени

А теперь интересная часть. Из правила «жив, пока хоть один счётчик не ноль» следует, что файл может существовать вообще **без имён** — пока его кто-то держит открытым.

![[unlink-open-fd.svg]]
*Рис. 2.4. Три состояния одной карточки: имя есть → имени нет, дескриптор есть → нет ни того, ни другого. Место возвращается только на третьем шаге.*

Это осмысленное решение, а не недосмотр. Программа, которая открыла файл, читает из него и вдруг получает «файла нет» посреди чтения, — это гораздо хуже, чем программа, которая спокойно дочитывает то, что открыла. Многие этим пользуются намеренно: создают временный файл, открывают его и **сразу удаляют имя**. Файл живёт, пока живёт процесс, и гарантированно исчезает вместе с ним — хоть при падении, хоть при `kill -9`, хоть при выдернутом питании.

Но у этого поведения есть цена, и вот она-то и портит ночи:

**Файл без имени невидим для всего, что ищет по именам.** `ls` его не покажет. `du` не посчитает. `find` не найдёт. А место он занимает.

Инструмент, который такие файлы видит, — `lsof` с ключом `+L1`, то есть «покажи открытые файлы, у которых меньше одной ссылки»:

```bash
kot@catbox:~$ sudo lsof +L1
COMMAND   PID   USER   FD   TYPE DEVICE    SIZE/OFF NLINK    NODE NAME
gallery  1842 photos    5w   REG    8,2 21474836480     0 1310755 /var/log/gallery/access.log (deleted)
```

Читаем по колонкам: `FD 5w` — дескриптор номер 5, открыт на запись. `NLINK 0` — имён не осталось, первый счётчик пуст. `SIZE/OFF` — 20 ГБ занятого места. `NAME` — то имя, под которым файл был открыт, с пометкой `(deleted)`.

Никакой магии тут нет: `lsof` не хранит имён сам, он читает `/proc/1842/fd/`, где ядро показывает ровно то же самое:

```bash
kot@catbox:~$ sudo ls -l /proc/1842/fd/5
l-wx------ 1 photos photos 64 Sep  1 09:40 /proc/1842/fd/5 -> '/var/log/gallery/access.log (deleted)'
```

Обрати внимание на тип `l`. Это симлинк — но особенный: он ведёт **не по пути, а прямо на открытую карточку**. Ядро подставило туда старое имя просто для человека.

И через него с безымянным файлом можно работать:

```bash
# прочитать — то есть восстановить
kot@catbox:~$ sudo cp /proc/1842/fd/5 /srv/recovered.log

# обрезать до нуля — то есть освободить место, не трогая процесс
kot@catbox:~$ sudo sh -c ': > /proc/1842/fd/5'
```

Оба трюка спасают, когда перезапускать процесс нельзя.

> [!warning] Оговорка про обрезание
> Если процесс писал в файл **не** в режиме `O_APPEND`, его позиция записи осталась там же, где была, — на отметке 20 ГБ. После обрезания следующая запись уйдёт по этому смещению, и файл снова покажет 20 ГБ длины, хоть и разреженной (про разреженные файлы — в подглаве [[01-Что такое файл]]). Место оно всё равно освободит, но `ls -lh` будет пугать.

Про `lsof` есть и практическая оговорка. На Ubuntu Server он стоит из коробки, на минимальной RHEL 9 — нет, а `dnf install lsof` на сервере с полностью забитым диском может и не сработать. Запасной вариант работает везде:

```bash
kot@catbox:~$ sudo find /proc/[0-9]*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null
/proc/1842/fd/5 -> /var/log/gallery/access.log (deleted)
```

## Карточки тоже кончаются

Последнее, что нужно знать перед разбором поломок: **количество карточек конечно**, и это отдельный ресурс, не связанный с местом на диске.

На ext4 таблица inode создаётся один раз, при форматировании, и потом её размер не меняется. По умолчанию `mkfs.ext4` заводит одну карточку на каждые 16 КБ диска: на корневом разделе `catbox`, а это 99 ГБ, получилось около 6,5 миллиона. Для фотографий по 3 МБ это в тысячи раз больше, чем нужно. А для кэша миниатюр по 8 КБ, PHP-сессий, очередей почты или слоёв контейнеров — может кончиться задолго до того, как кончится место.

XFS устроен иначе: он выделяет карточки по мере надобности, так что этот класс проблем на RHEL, где XFS по умолчанию, встречается заметно реже. Совсем он не исчезает — есть параметр `imaxpct`, ограничивающий долю ФС под карточки, — но упереться в него куда труднее.

Смотреть на этот ресурс нужно тем же `df`, только с ключом `-i`:

```bash
kot@catbox:~$ df -i /srv
Filesystem      Inodes   IUsed   IFree IUse% Mounted on
/dev/sda2      6488064  418223 6069841    7% /
```

Пока спокойно. Как выглядит, когда неспокойно, — сейчас увидим.

## Что нужно унести из этой подглавы

> [!summary] Семь утверждений
> 1. Жёсткая ссылка — второе имя для той же карточки. «Оригинала» нет, отличить нельзя.
> 2. Символическая ссылка — отдельный файл, внутри которого лежит строка пути. Она про буквы, а не про номера.
> 3. Отсюда все ограничения: жёсткая не уходит за пределы ФС и не бывает битой; символическая уходит куда угодно и бьётся легко.
> 4. У файла два счётчика: имена и открытые дескрипторы. Жив, пока хоть один не ноль.
> 5. `rm` — это `unlink`, «отцепить имя». Данные он не трогает.
> 6. Файл без имён невидим для `ls`, `du` и `find`, но занимает место. Ищется через `lsof +L1` или `/proc/*/fd`.
> 7. Карточки — отдельный конечный ресурс. `df -h` про него ничего не говорит, `df -i` говорит.

## Как это ломается

### «Ротировали лог — новый пустой, а старый растёт»

Галерея пишет `access.log`, он разросся, и я решил ротировать по-простому: `mv access.log access.log.1`, потом `touch access.log`. Через час новый файл всё ещё нулевого размера, а `access.log.1` продолжает расти.

Ничего не сломано. Просто `mv` внутри одной файловой системы **переименовывает строку в каталоге** — карточка та же самая. А дескриптор процесса указывает на карточку, минуя имена; процессу совершенно всё равно, как эта строка теперь называется. Он пишет туда, куда открыл.

Диагноз ставится одним взглядом:

```bash
kot@catbox:~$ sudo ls -l /proc/1842/fd/ | grep log
l-wx------ 1 photos photos 64 Sep  1 09:40 5 -> /var/log/gallery/access.log.1
```

Лечение — заставить процесс **переоткрыть** файл, то есть отпустить старую карточку и получить новую. У порядочных демонов для этого есть сигнал (обычно `SIGHUP` или `SIGUSR1`), и `logrotate` умеет его посылать через `postrotate`.

Если процесс переоткрывать не умеет, у `logrotate` есть `copytruncate`: скопировать содержимое в новый файл, а старый обрезать до нуля через ту же карточку. Между копированием и обрезанием можно потерять несколько строк — это цена за работу с программой, которая не умеет ротацию.

### «Диск полон, а `du` ничего не находит»

Продолжение той же истории, но хуже. Кто-то увидел растущий `access.log.1` и удалил его. `df` показывает 100%, `du -sh /` в сумме даёт на 20 ГБ меньше, чем занято, и никакие `find -size +1G` ничего не находят.

К этому моменту ты уже знаешь, что случилось: первый счётчик обнулили, второй остался — карточка с 20 ГБ блоков жива и невидима.

`lsof +L1` или обход `/proc/*/fd` показывают виновника, как в примере выше. Дальше выбор из трёх вариантов, по возрастанию грубости:

1. попросить процесс переоткрыть лог, если умеет;
2. обрезать файл через `/proc/PID/fd/N`;
3. перезапустить процесс.

Первые два не роняют сервис. Если данные из лога были нужны — сначала `cp /proc/PID/fd/N` куда-нибудь. Правда, «куда-нибудь» на полном диске придётся ещё поискать.

> [!warning] `kill -9` не всегда освобождает место
> Если удалённый файл держит не один процесс, а несколько, или дескриптор унаследовали дочерние процессы, — убийство одного из них ничего не даст. Второй счётчик уменьшится, но не до нуля. Смотри на весь список `lsof +L1`, а не на первую строку.

### «No space left on device, но `df -h` показывает 40% свободно»

Галерея перестала сохранять новые фотографии с ошибкой `No space left on device`. Первое, что делает любой человек, — `df -h`, и видит 20 свободных гигабайт. Второе, что стоит сделать любому человеку:

```bash
kot@catbox:~$ df -i /srv
Filesystem      Inodes   IUsed IFree IUse% Mounted on
/dev/sda2      6488064 6488064     0  100% /
```

Место есть, а карточек нет. Создать даже пустой файл невозможно — под него не из чего взять запись в таблице. Ядро сообщает об этом **тем же кодом ошибки**, что и про нехватку места, и это, честно говоря, самое запутывающее во всей ситуации.

Теперь надо понять, кто их съел. Шесть с половиной миллионов файлов — это точно не фотографии. Считаем файлы по каталогам, а не байты:

```bash
kot@catbox:~$ sudo du --inodes -x / 2>/dev/null | sort -n | tail -5
  12441  /usr
 184220  /var/lib
6265187  /var/cache/gallery/thumbs
6273904  /var/cache
6487602  /
```

Ключ `--inodes` считает штуки вместо байтов, `-x` не даёт `du` уходить на другие файловые системы — иначе он посчитает и `/proc`, и NAS.

Шесть миллионов миниатюр: галерея генерирует по четыре превью на каждое фото и никогда не чистит кэш. Чистим кэш, чиним настройку, идём спать.

А если бы оказалось, что карточки честно нужны — это не кэш, а рабочие данные, — то на ext4 вариант один: переформатировать с бо́льшим их количеством (`mkfs.ext4 -i 4096`, одна карточка на 4 КБ, или `-T small`). Добавить карточки в существующую ext4 нельзя; они появятся только при увеличении самого раздела, пропорционально. На XFS вопрос бы не встал.

### «Файл на месте, а команда говорит No such file»

После переноса `/srv/cats` на новый диск галерея перестала показывать «последнее фото». В каталоге всё выглядит нормально — пока не попробуешь открыть:

```bash
kot@catbox:/srv/cats$ ls -l latest.jpg
lrwxrwxrwx 1 kot kot 30 Aug 15 12:00 latest.jpg -> /mnt/old-disk/cats/2024/murzik.jpg

kot@catbox:/srv/cats$ cat latest.jpg
cat: latest.jpg: No such file or directory
```

Сообщение сбивает с толку: `ls` файл видит, `cat` — нет. Но они говорят о разных файлах.

`ls -l` смотрит на **сам симлинк** — и симлинк на месте, живой, 30 байт текста. `cat` идёт **по пути внутри симлинка**, а там ничего нет: старый диск отмонтирован. Это та самая абсолютная ссылка, которая не пережила переезд.

Найти все такие в дереве сразу:

```bash
kot@catbox:/srv/cats$ find . -xtype l
./latest.jpg
./2023/cover.jpg
```

`-xtype l` читается так: «после попытки пройти по ссылке тип всё ещё `l`» — то есть пройти не удалось.

Чинить — пересоздавать ссылки, на этот раз относительными:

```bash
kot@catbox:/srv/cats$ ln -sfn 2024/murzik.jpg latest.jpg
```

Ключ `-n` здесь важен, если ссылка ведёт на каталог: без него `ln` пройдёт по существующей ссылке и создаст новую **внутри** целевого каталога, вместо того чтобы заменить старую.

## Задачи для самопроверки

> [!question] Задача 1 · Два имени
> Создай файл, сделай на него жёсткую ссылку в другом каталоге. Допиши что-нибудь в файл через второе имя, потом удали первое.
>
> **Как понять, что получилось:** `ls -li` показывает один inode и `Links: 2` до удаления, а после удаления содержимое, включая дописанное, читается через оставшееся имя.

> [!question] Задача 2 · Кто рвёт ссылки
> Возьми пару из задачи 1 и отредактируй один из файлов через `sed -i`.
>
> **Как понять, что получилось:** `ls -li` показывает два разных inode, содержимое разошлось — и ты можешь объяснить, почему `echo >> файл` так бы не сделал.

> [!question] Задача 3 · Удалённый, но открытый
> Запусти в одном терминале `sleep 600 > /tmp/held.log` (или `tail -f`), в другом удали `/tmp/held.log`. Найди файл через `lsof +L1` и через `/proc/PID/fd`, восстанови его копию, потом освободи место обрезанием.
>
> **Как понять, что получилось:** `df` меняется только после обрезания или завершения `sleep`, а восстановленная копия читается.

> [!question] Задача 4 · Кончились карточки
> На своей VM создай маленький образ: `truncate -s 100M`, `mkfs.ext4 -N 200`, смонтируй через `-o loop` (подробно про это — в подглаве [[05-Монтирование и файловые системы]], но `man mount` пока хватит). Заполни его пустыми файлами до отказа.
>
> **Как понять, что получилось:** `touch` говорит `No space left on device`, `df -h` показывает почти пустой раздел, `df -i` — 100%.

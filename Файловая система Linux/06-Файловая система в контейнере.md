# Файловая система в контейнере: ничего нового

> [!abstract] Файловая система Linux · подглава 6 из 6
> Новая деталь ровно одна — overlayfs. Всё остальное в контейнере собрано из bind mount, tmpfs, дерева монтирований и inode, у которого имя не главное.

Галерея на `catbox` в конце концов переехала в Docker — не из моды, а потому что мне надоело чинить окружение после каждого обновления Python и хотелось откатываться одной командой.

В первую же неделю случилось то, что случается со всеми. Я загрузил через веб-интерфейс сотню фотографий, собрал новый образ, сделал `docker compose up` — и фотографии исчезли. Не «повредились», не «не открываются». Их просто не стало, как будто и не было.

Это не ошибка Docker. Это прямое следствие того, как устроена файловая система контейнера, — и всё нужное, чтобы её понять, у нас уже есть.

Смысл этой подглавы в том, что **контейнер не вводит ни одной новой сущности**. Он собран из деталей, которые уже лежат у нас на столе:

- **bind mount** и **tmpfs** — [[05-Монтирование и файловые системы|подглава 5]];
- **дерево монтирований** и то, что содержимое точки монтирования становится недоступным, — [[05-Монтирование и файловые системы|подглава 5]];
- **символьные устройства** с парой major/minor — [[03-Устройства и псевдофайлы|подглава 3]];
- **inode, у которого имя не главное**, — подглавы [[01-Что такое файл|1]] и [[02-Ссылки|2]].

Новая деталь ровно одна: файловая система **overlayfs**. С неё и начнём, причём соберём её руками, без всякого Docker, — чтобы стало видно, что магии нет.

## overlayfs руками

Overlayfs не хранит ничего сама. Она берёт несколько каталогов и показывает их как один, наложенными друг на друга. Соберём такую на `catbox`:

```bash
kot@catbox:~$ mkdir -p ov/base ov/app ov/upper ov/work ov/merged
kot@catbox:~$ echo "v1" > ov/base/config.yml
kot@catbox:~$ echo "hello" > ov/base/readme
kot@catbox:~$ echo "gallery binary" > ov/app/gallery
kot@catbox:~$ echo "noise" > ov/app/debug.log

kot@catbox:~$ sudo mount -t overlay overlay \
    -o lowerdir=ov/app:ov/base,upperdir=ov/upper,workdir=ov/work ov/merged

kot@catbox:~$ ls ov/merged
config.yml  debug.log  gallery  readme
```

Четыре опции:

- **`lowerdir`** — нижние слои, только для чтения. Их может быть много, через двоеточие, и **левый считается верхним**.
- **`upperdir`** — единственный слой, куда идёт запись.
- **`workdir`** — служебный каталог на той же ФС, что и upper; overlay нужен для атомарных операций, трогать его не надо.
- И точка монтирования — `merged`, где видно всё сразу.

Чтение устроено просто: имя ищется сверху вниз — сначала в `upper`, потом в `app`, потом в `base`, — и побеждает первое найденное. Интересное начинается с записи.

```bash
kot@catbox:~$ echo "v2" > ov/merged/config.yml
kot@catbox:~$ cat ov/base/config.yml ov/upper/config.yml
v1
v2
```

Файл `config.yml` лежал в `base`. Мы записали в него через `merged` — и `base` не изменился. Вместо этого overlay скопировал файл в `upper` и изменил копию.

Это называется **copy-up**, и это то самое copy-on-write, о котором все говорят применительно к контейнерам. Обрати внимание на цену: **копируется файл целиком, при первой же записи**, даже если ты изменил один байт. Для конфига это ничто. Для десятигигабайтной базы данных, лежащей в слое образа, — катастрофа.

Теперь удаление:

```bash
kot@catbox:~$ rm ov/merged/debug.log
kot@catbox:~$ ls ov/merged
config.yml  gallery  readme

kot@catbox:~$ ls -l ov/upper/
c--------- 1 root root 0, 0 Sep  2 14:10 debug.log
-rw-rw-r-- 1 kot  kot     3 Sep  2 14:08 config.yml
```

Из `app` удалить нельзя — он только для чтения. Поэтому overlay кладёт в `upper` файл с тем же именем и особым типом: **символьное устройство с major и minor, равными нулю**.

Вспомни `/dev` [[03-Устройства и псевдофайлы|из третьей подглавы]]: пара `(0, 0)` не соответствует никакому драйверу, обратиться к такому устройству невозможно. Overlay пользуется этим как маркером: «здесь дыра, всё, что ниже, не показывать». Такой файл называется **whiteout**. В `merged` его не видно, а в `upper` он лежит как обычный файл.

![[01-overlayfs.svg]]
*Рис. 6.1. Вся механика overlayfs: чтение сверху вниз, copy-up при записи, whiteout при удалении.*

Три правила — чтение сверху вниз, copy-up при записи, whiteout при удалении — это вся механика overlayfs. Всё остальное в контейнерах сводится к вопросу, какие каталоги подставить в `lowerdir` и `upperdir`.

> [!note] Ещё один случай: непрозрачный каталог
> У каталогов есть ещё один вариант. Если удалить целый каталог из нижнего слоя и создать пустой с тем же именем, overlay помечает его расширенным атрибутом `trusted.overlay.opaque` — «не смешивать с тем, что ниже». Механика та же, просто маркер лежит не файлом, а атрибутом.

## Из чего Docker собирает контейнер

### Образ — это стопка нижних слоёв

Каждая инструкция `RUN`, `COPY`, `ADD` в Dockerfile создаёт слой. Docker монтирует overlay из всех предыдущих слоёв, выполняет инструкцию, и получившийся `upperdir` становится новым слоем — со всеми copy-up'ами и whiteout'ами внутри.

Отсюда сразу объясняется старая загадка сборки: **`RUN rm -rf /var/lib/apt/lists` отдельной инструкцией не уменьшает образ**. Файлы остаются в нижнем слое, а сверху ложится whiteout — то есть образ даже слегка растёт. А `RUN apt install && rm -rf ...` в одной строке уменьшает, потому что удаление происходит внутри той же инструкции, до того как слой зафиксирован.

![[02-sloi-obraza.svg]]
*Рис. 6.2. Нижние слои образа общие для всех контейнеров, верхний слой — у каждого свой.*

Где всё это лежит физически:

```bash
kot@catbox:~$ docker inspect --format '{{.GraphDriver.Data.UpperDir}}' gallery
/var/lib/docker/overlay2/3f8a1c…d92e/diff

kot@catbox:~$ findmnt -t overlay
TARGET                                        SOURCE  FSTYPE  OPTIONS
/var/lib/docker/overlay2/3f8a1c…d92e/merged   overlay overlay rw,relatime,lowerdir=…,upperdir=…,workdir=…
```

Тот же самый `mount -t overlay`, что мы делали руками, с теми же четырьмя опциями. `LowerDir` — слои образа, общие для всех контейнеров из него: десять контейнеров из образа `ubuntu` не занимают в десять раз больше места. `UpperDir` — слой этого конкретного контейнера, и `docker diff gallery` покажет его содержимое списком изменений.

### Почему контейнер видит свой `/etc`

Внутри контейнера `ls /etc` показывает файлы из образа, а не с `catbox`. Никакого отдельного диска у контейнера нет — и вот здесь надо аккуратно поправить одно утверждение [[05-Монтирование и файловые системы|из пятой подглавы]].

Мы говорили: «у Linux одно дерево имён с корнем `/`». Точнее будет так: **одно дерево у каждого процесса**, и деревьев может быть несколько. Механизм называется **mount namespace**.

При запуске контейнера Docker создаёт для его процесса копию дерева монтирований и в этой копии:

1. делает `merged` корнем — системным вызовом `pivot_root`;
2. монтирует свежий `/proc`, чтобы контейнер видел только свои процессы;
3. добавляет всё, что попросили через `-v` и `--tmpfs`.

Подробно про namespaces — в главе [[Процессы]]. Для нас важно, что это **отдельное дерево на том же ядре и тех же дисках**. Не виртуальная машина, не эмуляция — просто другой набор правил подстановки при обходе пути.

С хоста в это дерево можно заглянуть двумя способами. `/proc/PID/root` — симлинк на корень процесса в его пространстве, так что `ls /proc/1842/root/etc` покажет `/etc` контейнера. А `nsenter` выполнит команду прямо внутри его mount namespace:

```bash
kot@catbox:~$ sudo nsenter -t 1842 -m findmnt -t overlay,ext4,tmpfs
TARGET             SOURCE                                              FSTYPE  OPTIONS
/                  overlay                                             overlay rw,relatime,lowerdir=…
├─/data            /dev/sdb1[/cats]                                    ext4    rw,noatime
├─/var/lib/db      /dev/sda2[/var/lib/docker/volumes/gallery-db/_data] ext4    rw,relatime
├─/etc/resolv.conf /dev/sda2[/var/lib/docker/containers/3f8a…/resolv.conf] ext4 rw,relatime
├─/etc/hostname    /dev/sda2[/var/lib/docker/containers/3f8a…/hostname]  ext4  rw,relatime
├─/etc/hosts       /dev/sda2[/var/lib/docker/containers/3f8a…/hosts]     ext4  rw,relatime
└─/tmp             tmpfs                                               tmpfs   rw,nosuid,nodev
```

Вот она, вся файловая система контейнера, в шести строках — и каждую строку мы уже умеем читать.

Корень — overlay. `/data` — bind mount каталога с котами с `sdb1`, и квадратные скобки в `SOURCE` те же самые, что были у bind mount'ов [[05-Монтирование и файловые системы|в пятой подглаве]]. `/var/lib/db` — тоже bind mount, только каталога внутри `/var/lib/docker/volumes`; это и есть named volume. `/tmp` — tmpfs, потому что контейнер запущен с `--tmpfs /tmp`.

И три строки посередине объясняют вопрос, который всплывает у каждого: **почему правка `/etc/hosts` в Dockerfile не работает**. Docker генерирует `hosts`, `hostname` и `resolv.conf` для каждого контейнера отдельно и bind-монтирует их поверх overlay. Файл в слое образа существует — но путь до него сворачивает раньше, ровно как каталог под точкой монтирования [[05-Монтирование и файловые системы|из пятой подглавы]]. Менять их нужно средствами Docker: `--add-host`, `--dns`, `--hostname`.

## Куда уходит запись

Теперь можно ответить на вопрос, с которого началась подглава.

![[03-kuda-uhodit-zapis.svg]]
*Рис. 6.3. Пять мест, куда может уйти запись из контейнера, и что с каждым делает `docker rm`.*

Схема показывает, где данные лежат физически. А вот что с ними происходит по командам — то, ради чего всё это и нужно помнить:

| Куда пишет контейнер                                  | `docker stop` | `docker rm`  | Пересоздание из нового образа |
| ----------------------------------------------------- | ------------- | ------------ | ----------------------------- |
| Верхний слой overlay (`/app/uploads`, `/etc`, `/usr`) | переживёт     | **удалится** | **удалится**                  |
| bind mount (`-v /srv/cats:/data`)                     | переживёт     | переживёт    | переживёт                     |
| named volume                                          | переживёт     | переживёт    | переживёт                     |
| tmpfs                                                 | **исчезнет**  | исчезнет     | исчезнет                      |

Третья колонка и есть ответ. `docker compose up` после смены образа удаляет старый контейнер и создаёт новый с **пустым** верхним слоем. Мои фотографии лежали в `/app/uploads`, за которым не было никакого монтирования, — то есть в верхнем слое.

Отсюда практическое различие между двумя вариантами хранения, которые формально делают одно и то же:

- **bind mount** — когда данные нужны и вне Docker, как наши коты: их читает ещё и скрипт бэкапа, и я сам через `ssh`.
- **named volume** — когда данные нужны только контейнеру: база, индекс, состояние. Docker создаёт каталог сам, `docker rm` его не трогает, `docker volume ls` его показывает, и он не зависит от того, как устроен хост.

И есть пятое место, куда контейнер пишет, не зная об этом, — **`stdout`**. Docker перехватывает поток и складывает его в файл `/var/lib/docker/containers/<id>/<id>-json.log`. Файл живёт вместе с контейнером, растёт неограниченно и по умолчанию не ротируется. Держи это в голове до раздела поломок.

## Мост к Kubernetes

Механика там та же самая, потому что под Kubernetes тот же Linux и тот же overlayfs — просто монтирует его не Docker, а `containerd`, и слои лежат в `/var/lib/containerd`. Корень контейнера так же эфемерен: `kubectl delete pod` делает с верхним слоем ровно то же, что `docker rm`.

Меняются в основном имена. Соответствие такое:

| Docker                          | Kubernetes              | Что это физически                                                                                                                |
| ------------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `--tmpfs` или временный каталог | `emptyDir`              | каталог в `/var/lib/kubelet/pods/<uid>/volumes/`, bind-монтированный в контейнеры пода (или tmpfs при `medium: Memory`)          |
| `-v /srv/cats:/data`            | `hostPath`              | bind mount каталога ноды, со всеми последствиями привязки к конкретной машине                                                    |
| named volume                    | `PersistentVolumeClaim` | облачный диск, том Ceph или iSCSI: блочное устройство подключается к ноде, монтируется kubelet'ом и bind-монтируется в контейнер |

Практически полезно здесь одно. Каждый шаг за этими словами — обычные `mount`, `umount`, иногда `mkfs` при первом использовании — происходит **на ноде** и виден обычными инструментами [[05-Монтирование и файловые системы|из пятой подглавы]]. Поэтому когда PVC «не монтируется», диагностика идёт через `journalctl -u kubelet` и `findmnt` на ноде, а не через `kubectl describe`. А `emptyDir` живёт ровно столько, сколько под: перезапуск контейнера внутри пода его не трогает, удаление пода — стирает.

## Что нужно унести из этой подглавы

> [!summary] Семь утверждений
> 1. Overlayfs накладывает каталоги друг на друга: чтение сверху вниз, copy-up при записи, whiteout при удалении.
> 2. Copy-up копирует файл целиком — большие файлы в слое образа этого не прощают.
> 3. Образ — стопка нижних слоёв, общая для всех контейнеров. Контейнер — свой верхний слой.
> 4. `RUN rm` отдельной инструкцией образ не уменьшает.
> 5. Корень контейнера — это mount namespace плюс `pivot_root`: другое дерево на тех же дисках.
> 6. Запись уходит в одно из пяти мест, и `docker rm` уничтожает только верхний слой.
> 7. Всё остальное — bind mount, tmpfs, обычные файлы хоста. Ничего нового.

## Как это ломается

### «Загрузил фотографии, обновил образ — фотографий нет»

Тот самый сценарий. Галерея сохраняла загрузки в `/app/uploads`; `/app` не был ни volume, ни bind mount; `docker compose up` с новым образом пересоздал контейнер.

Если старый контейнер ещё существует — `compose` его удаляет, но `docker run` без `--rm` после `stop` не удаляет, — данные на месте:

```bash
kot@catbox:~$ docker ps -a --filter name=gallery
CONTAINER ID   IMAGE           STATUS                   NAMES
9c2e1a4f7b03   gallery:1.4     Exited (0) 2 hours ago   gallery-old

kot@catbox:~$ docker diff gallery-old | grep uploads | head -3
A /app/uploads
A /app/uploads/IMG_4412.jpg
A /app/uploads/IMG_4413.jpg

kot@catbox:~$ docker cp gallery-old:/app/uploads ./recovered
```

`docker cp` работает с остановленным контейнером: он просто читает `upperdir` напрямую, никакого запуска не требуется. Если же контейнер удалён — данных нет, и это тот случай, когда `rm` действительно значит `rm`.

Починка на будущее — volume или bind mount на `/app/uploads`. И правило перед деплоем: `docker diff` на старом контейнере. Если он показывает что-то, кроме логов и временных файлов, — сервис пишет туда, куда не должен, и это заметно до потери, а не после.

### «`/var/lib/docker` забил диск»

`df` показывает 100% на корне, `du -xsh /var/lib/docker` — 80 ГБ. Что внутри, Docker расскажет сам:

```bash
kot@catbox:~$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          23        4         14.2GB    11.8GB (83%)
Containers      9         3         2.1GB     1.9GB (90%)
Local Volumes   6         2         3.4GB     2.8GB (82%)
Build Cache     147       0         9.6GB     9.6GB
```

Это 30 ГБ. Где ещё 50 — `docker system df` не скажет, потому что это не его данные:

```bash
kot@catbox:~$ sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail -1
51G	/var/lib/docker/containers/3f8a1c…/3f8a1c…-json.log
```

Галерея пишет в `stdout` по строке на запрос, полгода, без ротации.

Немедленное лечение — **обрезать, а не удалять**: `sudo truncate -s 0` на этот файл. Именно `truncate`, потому что Docker держит его открытым, и `rm` даст ровно тот сценарий [[02-Ссылки|из второй подглавы]]: имя исчезло, дескриптор остался, 51 ГБ по-прежнему заняты и теперь невидимы для `du`.

Постоянное лечение — включить ротацию логов в `/etc/docker/daemon.json` (`log-driver` и `log-opts` с `max-size`, `max-file`); настройка применится к контейнерам, созданным после перезапуска демона. Остальное чистится через `docker system prune` — с одной оговоркой.

> [!warning] `docker system prune --volumes` удаляет данные
> Без `--volumes` команда трогает только остановленные контейнеры, неиспользуемые образы и кэш сборки — это безопасно. С `--volumes` она удаляет все тома, не подключённые к **работающему** контейнеру. Том остановленной базы данных — именно такой. Перед этим флагом — `docker volume ls` и глазами.

### «Поправил конфиг на хосте, контейнер видит старый»

Конфиг галереи подключён одним файлом: `-v ./gallery.yml:/etc/gallery.yml`. Я открыл его в `vim` на хосте, поправил, сохранил. Внутри контейнера `cat /etc/gallery.yml` показывает старое содержимое. Перезапуск контейнера не помогает — помогает только пересоздание.

Это [[02-Ссылки|вторая подглава]] в чистом виде. **Bind mount привязан к карточке, а не к имени.** `vim` при сохранении пишет новый файл и переименовывает его поверх старого — то есть создаёт новый inode. Имя `gallery.yml` теперь указывает на него, а bind mount в контейнере — по-прежнему на старый, который никуда не делся, потому что у него есть держатель.

Проверка занимает две команды:

```bash
kot@catbox:~$ ls -i gallery.yml
1310801 gallery.yml

kot@catbox:~$ sudo nsenter -t 1842 -m ls -i /etc/gallery.yml
1310744 /etc/gallery.yml
```

Разные карточки. То же самое сделает `sed -i` и большинство редакторов.

Что **не** сломает: запись в существующий inode — `echo ... > gallery.yml`, или `:set backupcopy=yes` в vim. Что **лучше**: монтировать каталог, а не файл. Тогда bind mount привязан к карточке каталога, а файлы внутри можно пересоздавать сколько угодно.

### «Permission denied в volume, хотя на хосте всё открыто»

Контейнер запущен от пользователя `photos` (uid 1000 внутри). Named volume для базы Docker создал сам — с владельцем `root:root`, потому что демон работает от root. Контейнер не может в него писать.

Ключевая мысль: **uid внутри контейнера — тот же uid, что снаружи.** У ядра одно пространство пользователей, если специально не включены user namespaces. Число 1000 внутри — это число 1000 на хосте, и права проверяются по числу, а не по имени; имена вообще живут в `/etc/passwd`, а он внутри и снаружи разный.

Диагностика — `ls -ln` (числовые uid) с обеих сторон:

```bash
kot@catbox:~$ sudo ls -ln /var/lib/docker/volumes/gallery-db/_data
drwxr-xr-x 2 0 0 4096 Sep  2 15:00 .
```

Владелец 0 — root. Починка: `chown 1000:1000` на каталог, или `--user`, или entrypoint, который делает `chown` при первом старте (так поступают официальные образы баз данных).

Обратная сторона той же медали: файлы, которые контейнер от root создал в bind mount, на хосте тоже принадлежат root, и удалить их без `sudo` не выйдет. Подробнее про uid и права — в главе [[Пользователи, группы и права]].

## Задачи для самопроверки

> [!question] Задача 1 · Overlay без Docker
> Собери overlay из двух нижних слоёв и одного верхнего, как в начале подглавы. Измени файл из нижнего слоя, удали файл из среднего, создай новый.
>
> **Как понять, что получилось:** в `upper` лежат copy-up-копия, whiteout типа `c` с парой `0, 0` и новый файл, а нижние слои не изменились байт в байт.

> [!question] Задача 2 · Найти верхний слой контейнера
> Запусти любой контейнер, создай внутри файл, найди его на хосте через `docker inspect … UpperDir` — не используя `docker cp`.
>
> **Как понять, что получилось:** `ls -i` файла на хосте и `nsenter … ls -i` внутри дают один и тот же номер карточки.

> [!question] Задача 3 · Четыре места для записи
> Запусти контейнер с bind mount каталога хоста, named volume и `--tmpfs`, запиши файл в каждое из четырёх мест (включая верхний слой). Останови, потом удали контейнер.
>
> **Как понять, что получилось:** ты заранее написал на бумажке, какие файлы переживут `stop` и какие `rm`, и оказался прав.

> [!question] Задача 4 · Сломать bind mount одного файла
> Подключи файл через `-v`, отредактируй его на хосте сначала через `vim`, потом через `echo >`.
>
> **Как понять, что получилось:** после `vim` контейнер видит старое содержимое и другой inode, после `echo` — новое, и ты можешь объяснить, почему монтирование каталога избавляет от проблемы.

> [!question] Задача 5 · Whiteout в образе
> Напиши Dockerfile с `COPY` большого файла и отдельным `RUN rm` его же. Собери, посмотри `docker history` и размер образа. Затем найди слой с whiteout'ом в `/var/lib/docker/overlay2`.
>
> **Как понять, что получилось:** образ не уменьшился, а в одном из `diff/` лежит символьное устройство `0, 0` с именем удалённого файла.

## Конец главы

Шесть подглав назад мы начали с вопроса, который звучал глупо: что такое файл. Ответ — карточка, inode, — сначала выглядел как формальность, а потом объяснил всё остальное: почему `rm` не удаляет данные, почему диск бывает полон без файлов, почему `df` и `du` не сходятся и почему конфиг в контейнере не обновился после `vim`.

Полезно заметить, чего в этой главе не было. Не было отдельного механизма для устройств, отдельного — для контейнеров, отдельного — для сети. Была одна цепочка `имя → карточка → данные`, у которой по-разному устроено последнее звено, и одно дерево, сшитое монтированиями. Всё остальное — комбинации.

Именно поэтому знание здесь окупается: инструменты меняются каждые пять лет, а `stat`, `findmnt`, `lsof` и `/proc` показывают одно и то же и в 2005 году, и внутри контейнера в кластере.
